## Core architecture rule

**Engines comes first. CTA is independent and replaceable.**

```text
CLI ───────────┐
HTTP/API ──────┤
WebChat ───────┤
Telegram ──────┤── CTA boundary ── ENGINES
WhatsApp ──────┘
```

Telegram and WhatsApp add transport/connection behavior only. They do not add provider-specific Customer, Workflow, Services or Scheduler truth.

## Customer registration policy

The first messaging business slice remains intentionally limited to `RegisterNewCustomer` with V2 minimum:

```text
customer.name
customer.contact.phone
customer.contact.email
```

Customer/Temporal owns that policy. Provider adapters only normalize and render.

## C2P — Telegram official Bot API ✅ SEALED

Physically proven:

```text
real Telegram account
→ official Telegram Bot API
→ getUpdates / sendMessage

→ CanonicalChannelEnvelope
→ CustomerRegistrationChannelExecutionCore
```

Human provider proof also covered invalid phone/email rejection with recovery to successful completion. Telegram Web did not visibly render native `request_contact`; typed phone remains an explicit supported path and the provider gate remains sealed.

## C4P — Meta WhatsApp Cloud API next

The next bounded gate targets the official Meta-hosted WhatsApp Cloud API behind the already-existing `WhatsAppTransportPort`.

Target architecture:

```text
real WhatsApp user
  ↓
Meta WhatsApp Cloud API
  ↓
public HTTPS webhook
  ↓
Meta webhook verification + HMAC authenticity
  ↓
Meta payload normalization
  ↓
WhatsAppAdapter
  ↓
CanonicalChannelEnvelope
  ↓
CustomerRegistrationChannelExecutionCore
  ↓
PostgreSQL
  ↓
Temporal RegisterNewCustomer
  ↓
Customer persistence
  ↓
Graph API outbound reply
```

The first physical implementation target is direct Meta Cloud API. Kapso remains an optional later implementation below the same transport port.

For local physical development, a temporary public HTTPS tunnel is acceptable as test infrastructure. It does not become a production dependency or business authority.
